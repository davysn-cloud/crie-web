# Audit — 2026-04-15

Delta entre [[schema|03_backend/schema.md]] (rascunho canônico) e o estado real das migrations em `supabase/migrations/`. Este doc **não altera** migrations existentes; serve como referência para (a) realinhar `schema.md` e (b) planejar as novas migrations.

## Sumário executivo
- `schema.md` está **significativamente defasado**. Usa nomes `workspaces`/`clients`/`client_members`/`posts`/`post_media`/`approvals` que **não existem** no banco.
- O banco real usa uma hierarquia **`agencies → agency_members → workspaces (por cliente/marca) → workspace_members → post_cards`**, com RLS via `is_agency_member()` / `is_workspace_member()`. É uma topologia melhor; o schema.md é que precisa acompanhar.
- Existem 3 tabelas reais (`agency_invites`, `comments`, `stage_transitions`) que o schema.md nem menciona.
- 6 tabelas do schema.md (`clients`, `client_members`, `posts`, `post_media`, `approvals`, `workspaces` modelo antigo) ou **não existem** ou **foram renomeadas/remodeladas**.
- **Contagem real:** 11 tabelas aplicadas (agências de domínio) + 3 auxiliares de flow. O briefing cita "9 tabelas" — número desatualizado.

## RLS auditado

### OK (presentes e corretas)
- `agencies`, `agency_members`, `workspaces`, `workspace_members`, `brand_profiles`, `post_cards`, `copy_versions`, `asset_versions`, `agency_invites`, `comments`, `stage_transitions` — todas com `ENABLE ROW LEVEL SECURITY` + policies de `SELECT/INSERT/UPDATE/DELETE` apropriadas.
- Helpers `is_agency_member(uuid)`, `is_workspace_member(uuid)`, `get_agency_id_for_workspace(uuid)` são `SECURITY DEFINER STABLE` — padrão correto.
- `can_access_comment_target()` é plpgsql `SECURITY DEFINER STABLE` — ok.

### Gaps / pendências
- `agencies` **não tem policy de DELETE** — ok para MVP (não queremos deletar agência fácil), mas deve ser documentado.
- `agency_invites`: tem `invites_public_select` para `anon`, **sem filtro por expiração** (`accepted_at IS NULL` não cobre "convite de 2019"). Falta coluna `expires_at`.
- `stage_transitions`: sem policy de UPDATE/DELETE — **correto**, é append-only. Documentar.
- `copy_versions` / `asset_versions`: **não têm policy de DELETE**. Versões nunca deveriam ser deletadas (são histórico). Deixar explícito (comentário ou revogação).
- Storage buckets `brand-assets` e `post-assets` são **públicos** com leitura `TO public` — aceitável para MVP de aprovação (URLs não adivinháveis), mas **deve virar ADR**.
